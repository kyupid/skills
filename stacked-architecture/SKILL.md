# 아키텍처는 완성품이 아니라 쌓인 순서로 설명한다

## 언제 쓰나

- 시스템 구조를 **남에게** 소개하는 자료를 만들 때. 발표, 기술 블로그, 온보딩 문서, 사내 공유.
- 안 쓴다: 컴포넌트 하나의 동작 설명, 코드 리뷰, 사용자가 대화로 짧게 물어본 구조 질문. 그건 그냥 답하거나 `design-rationale` 로 충분하다.

`design-rationale` 과 짝이다. 그쪽은 **확인한 사실과 짐작을 가르는 규율**이고, 이 스킬은 **그 사실을 어떤 형식으로 쌓아 보여줄지**다. 자료를 만들기 전에 `design-rationale` 의 기준(특히 "치르는 대가"와 "내가 모르는 것")을 먼저 적용한다.

## 핵심: 겹을 나누는 기준은 컴포넌트가 아니라 문제다

가장 흔한 실패는 완성된 구조를 부위별로 나열하는 것이다. "인증 모듈이 있고, 캐시가 있고, 큐가 있고..." 읽는 사람은 **왜 그게 거기 있는지 모른 채 이름만** 얻는다. 이름은 저장소를 열면 나온다. 자료가 줘야 하는 건 순서다.

겹 하나는 이 세 줄로 이뤄진다.

1. **문제 한 줄.** 앞의 상태로는 감당이 안 되는 것. 반드시 앞 겹의 결과여야 한다.
2. **그래서 붙인 부품.** 하나다. 두 개가 필요하면 겹이 두 개인 것이다.
3. **치르는 대가.** 필수다.

대가가 빠지면 설명이 아니라 홍보다. 그리고 대가는 지어내면 안 된다. 코드에서 찾는다.

- 나중에 들어간 예외 처리와 hotfix
- "주의", "바꾸지 말 것", "이 순서 유지" 류의 주석
- 하드코딩된 상한값 (상한이 있다는 건 넘쳐본 적이 있다는 뜻)
- 롤백 이력, 폐기된 패키지
- 주석에 남은 날짜·실측치·PR 번호

이런 흔적이 안 보이면 아직 덜 본 것이다. 다 잘 돌아가는 시스템은 없다.

## 순서는 개발 순서가 아니라 의존 순서

**00번은 반드시 "아무것도 없는 상태"에서 시작한다.** 부품 한두 개만 놓고, 그것만으로는 왜 안 되는지를 보여준다. 그 실패가 01번의 존재 이유가 된다. 여기서 시작하지 않으면 나머지 겹이 전부 "원래 있던 것" 처럼 읽힌다.

겹은 7~12개가 적정하다. 5개 이하면 굳이 이 형식일 필요가 없고, 15개를 넘으면 성격이 비슷한 것끼리 합친다.

마지막 한두 겹은 보통 **전체를 감싸거나 전체에서 걷어오는 것**이 온다. 배포 경계(실행 파일 하나, 컨테이너, VPC), 관측(기록·대시보드), 권한 경계 같은 것들이다. 그림이 닫히는 느낌을 주므로 아껴뒀다가 마지막에 쓴다.

## 사전 조사: 설계 문서를 믿지 말 것

**반드시 현재 코드를 본다.** 저장소에 있는 설계 문서는 대부분 낡았고, 낡은 문서 한 장이 발표 전체를 틀리게 만든다.

실제로 겪은 것: 설계 문서에 당당히 적힌 패키지 두 개가 지금 코드에는 디렉토리째 없었고, 문서가 17개라고 한 항목이 실제로는 46개였다. 문서만 읽고 썼으면 존재하지 않는 컴포넌트를 발표할 뻔했다.

봐야 할 순서:

| 무엇 | 왜 |
|---|---|
| repo 루트와 각 패키지의 `CLAUDE.md` / `README` | "바꾸지 말 것" 목록이 있으면 거기가 대가의 금광이다 |
| 팩토리 · DI 조립부 · 라우팅 등록부 | 실제로 살아 있는 컴포넌트 목록. 문서보다 이게 정본이다 |
| 상한값·기본값이 박힌 구조체 초기화 | 숫자와 그 위 주석이 사고 기록이다 |
| 최근 커밋과 폐기된 디렉토리 | 문서와 코드가 어긋나는 지점 |

## 만드는 순서

### 1. 사실을 모은다
위 표대로 읽는다. 서브에이전트를 쓰라는 지시가 없으면 직접 읽는다.

### 2. 겹 목록을 먼저 확정하고 사용자에게 보여준다
HTML 을 쓰기 전에 이 표부터 합의한다. 여기가 틀리면 뒤가 전부 헛수고다.

| 번호 | 문제 | 붙는 부품 | 대가 | 배선 변화 |
|---|---|---|---|---|
| 00 | (아무것도 못 하는 상태) | 코어 하나 | | |
| 01 | ... | ... | ... | |
| 06 | ... | 가드 | ... | 직통 끊기고 중간에 낌 |

### 3. 최종 다이어그램의 좌표를 먼저 잡는다
**겹마다 다른 그림을 그리지 않는다.** 완성된 구조 하나를 좌표로 확정하고, 각 요소에 `data-step` 만 붙인다. 표시·숨김으로 쌓임을 만든다. 그림을 11장 그리면 유지가 안 되고 좌표가 어긋난다.

좌표 요령:

- 주 흐름 하나(입력 → 입구 → 코어 → 실행 → 외부)를 **중앙 행**에 가로로 놓는다
- 나중에 붙는 부속(예산 계수기, 폴백, 보관소, 기록)은 **위·아래 행**에 건다
- 종횡비 2.2:1 안팎. 화면 상단 40% 정도만 차지해야 본문이 같이 읽힌다
- 상자 제목 13px, 부제 10px. 좌표는 눈대중 말고 격자에 맞춘다

### 4. 배선이 바뀌는 지점을 반드시 넣는다
이게 이 형식의 핵심이다. 부품이 **붙기만** 하면 그냥 목록이 길어지는 것이고, 기존 선이 끊기고 다시 이어져야 "구조가 바뀐다"는 느낌이 난다.

- 입구가 앞으로 한 칸 옮겨간다 (판별기가 생기면서 직통 진입이 사라짐)
- 직통 선이 끊기고 중간 노드가 낀다 (가드가 생기면서 코어→외부 직통이 사라짐)
- 하나였던 입력이 둘로 갈라진다 (캐시 때문에 정적/동적 블록 분리)

템플릿에서는 `data-until` 로 표현한다. `data-step="1" data-until="5"` 는 1번에 생겼다가 6번에서 대체된다는 뜻이다. 겹 목록 표의 "배선 변화" 칸이 여기로 온다.

### 5. `template.html` 을 복사해서 채운다
이 디렉토리의 `template.html` 이 동작하는 뼈대다. 붙박이 다이어그램, 스크롤 연동, 새 부품 강조, 진행 눈금, 라이트/다크 대응이 다 들어 있다. 내용만 갈아끼운다.

**팔레트와 활자는 주제에 맞게 다시 고른다.** 템플릿의 청동녹은 예시로 고른 색이지 기본값이 아니다. 그대로 쓰면 매번 같은 문서가 나온다. `artifact-design` 스킬의 기준을 적용한다.

### 6. 비유를 썼다면 기술용어 표기도 같이 낸다

낯선 구조를 설명할 때 비유는 잘 먹힌다. TLS 자료에서 세션 키를 "열쇠", 네트워크 경로를 "전선", 인증서를 "신분증"이라고 부르니 처음 보는 사람이 바로 따라왔다. 문제는 그 다음이다. 읽는 사람이 둘로 갈린다.

- 처음 보는 사람: 비유가 있어야 넘어간다
- 이미 아는 사람: 비유가 걸리적거린다. "열쇠"라고 하면 대칭키인지 개인키인지 모르겠고, 발표 뒤에 남는 단어가 우리 팀이 실제로 쓰는 말이 아니다

한쪽만 고르지 말고 **버튼으로 갈아끼운다.** 붙박이 다이어그램 오른쪽에 `비유 / 기술용어` 두 칸을 두면, 같은 문서를 두 청중에게 그대로 쓸 수 있다. 기본값은 비유 쪽이다.

`template.html` 에 다 들어 있다. 채울 곳은 두 군데다.

| 어디 | 어떻게 |
|---|---|
| 그림 글자, 읽기창 `data-title`/`data-add` | `<script>` 안 `TERMS` 에 `"비유": "기술용어"` 로 적는다. 글자가 **정확히 같아야** 걸린다 |
| 본문 낱말·문장 | `<t data-x="기술용어">비유</t>` 로 감싼다 |

원본(비유)은 JS 가 `data-fig` 에 기억해두므로 따로 적지 않는다. `TERMS` 를 비우고 `<t>` 도 안 쓰면 버튼은 저절로 숨는다. 비유를 안 쓴 자료라면 그냥 두면 된다.

지킬 것:

1. **고유명사는 바꾸지 않는다.** 코드에 있는 이름, 설정 키, 파일 경로, 실측치, `pre` 안의 도식. 그건 검색해서 찾아야 하는 값이고, `pre` 는 글자 수가 바뀌면 정렬이 깨진다.
2. **한국어는 문장 단위로 감싼다.** 활용 때문에 낱말만 갈면 문장이 부서진다. "잠근 쪽과 푸는 쪽이 같은 열쇠를 써야" 를 낱말로 처리하면 답이 없다. 통째로 "암호화하는 쪽과 복호화하는 쪽이 같은 키를 써야" 로 감싼다.
3. **기술용어 쪽이 더 정확해야 한다.** 비유의 직역이 아니라 그 분야에서 실제로 쓰는 이름을 적는다. "전선을 보는 사람"은 "전선 감시자"가 아니라 "중간자 (MITM)" 다.
4. **비유 쪽 문장을 먼저 완성한다.** 기술용어부터 쓰고 비유를 덧붙이면 비유가 장식이 된다. 순서가 거꾸로다.

TLS 자료의 실제 사전 (감을 잡는 용도):

| 비유 | 기술용어 |
|---|---|
| 전선 | 네트워크 경로 · TCP 연결 |
| 세션 열쇠 | 세션 키 (대칭키) |
| 잠긴 레코드 / 덩어리 | TLS 레코드 (암호문) |
| 잠근다 / 푼다 | 암호화한다 / 복호화한다 |
| 신분증 | 인증서 |
| 발급기관 | 인증기관 (CA) |
| 봉인 | 인증 태그 |
| 전선을 보는 사람 | 중간자 (MITM) |

발행 전에 **두 모드를 다 확인한다.** 헤드리스 크롬으로 충분하다.

```bash
CH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
# 기술용어 모드로 켜서 DOM 을 뜯어본다. 오류가 나면 title 이 ERR 로 바뀌게 해둔다
"$CH" --headless=new --disable-gpu --virtual-time-budget=3000 --dump-dom "file://$PWD/preview.html"
```

`preview.html` 은 문서 끝에 `document.querySelector('[data-mode="tech"]').click()` 한 줄을 붙인 사본이다. 바뀐 문자열이 실제로 들어갔는지 `grep` 으로 본다. 스크린샷은 스크롤 위치 때문에 빈 화면이 나오기 쉬우니 문자열 확인이 확실하다.

### 7. Artifact 로 발행한다
제목은 짧은 고유명사구로. 설명은 `description` 파라미터에 넣는다.

## 마지막에 사용자에게 확인할 것

자료를 넘기면서 이 세 가지는 반드시 같이 말한다. 사용자가 모르고 발표하면 사고가 난다.

1. **공개 범위.** 사고 날짜, 장애 시간, 실측 비용·실패율을 외부에 내도 되는 범위인지. 안 되면 "운영 중 실측" 정도로 뭉갤 수 있다.
2. **청중.** 개발자 대상인지 고객 대상인지에 따라 남길 겹이 다르다. 고객 대상이면 보통 안전·배포 겹만 남기고 내부 최적화 겹은 걷어낸다. 청중이 섞여 있으면 6번의 표기 전환 버튼이 그 자리를 메운다.
3. **내가 모르는 것.** 코드로 확인 못 한 설계 의도는 문서 본문에 넣지 말고, 사용자에게 따로 알려서 채우게 한다. 지어낸 이유는 그대로 남에게 전달된다.
